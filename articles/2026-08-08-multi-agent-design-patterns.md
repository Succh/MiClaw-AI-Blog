# 别急着拆分Agent：Google横评180种配置后，64%的场景单Agent就够了

> 作者：Succh | 发布时间：2026-08-08 | 阅读时长：6分钟

## 引言

2026年，多Agent系统已经从学术概念变成了工程现实。企业里合规审查需要跨5个文档库推理，客户支持需要跨3个系统查询，单个Agent的上下文窗口和工具数量似乎已经到了极限。于是"拆分"成了流行词——把一个Agent拆成三个、五个、十个，像搭积木一样堆出一个多Agent系统。

但Google Research在横评了180种Agent配置后，给出了一个反直觉的结论：在64%的基准测试中，单Agent（配更多工具）与多Agent系统表现持平。多Agent平均仅提升2.1个百分点准确率，但成本翻倍。

这不是说多Agent没用，而是说：**你可能还没到需要它的阶段，就已经在为它买单了。**

## 核心观点

### 一、多Agent的三道"物理墙"

任何多Agent系统都绕不开三道硬约束，而且每一道都有数学公式可以量化。

**Token膨胀**是最直接的成本杀手。Anthropic的数据显示，从单Agent到多Agent，Token消耗从约4倍膨胀到约15倍。原因很简单：每个Agent都需要携带完整的工具描述和系统提示，而这些内容60-80%是静态重复的。你有5个Agent，就等于把同一份工具手册抄了5遍。

**延迟累积**更隐蔽。Pipeline模式下，每增加一个Agent，延迟就增加约500毫秒。公式很残酷：总延迟 = 各Agent延迟之和 + 跳数 × 每跳延迟。5个Agent串联的Pipeline，光是通信延迟就要吃掉2.5秒。

**N²冲突诅咒**则是架构师的噩梦。冲突对数公式是N(N-1)/2——5个Agent产生10个冲突对，10个Agent产生45个冲突对。这意味着扁平化架构在Agent数量增加时会迅速失控，你不得不引入层级结构来管理冲突。

### 二、四大"甜点区"，对号入座

不要被"10种编排模式"吓住。所有模式可以按Agent数量和任务结构，划分到四个甜点区：

**1-3个Agent、确定性任务**：单Agent可能就够了。如果确实需要拆分，Pipeline（线性传递）或Orchestrator-Worker（中央调度）是最安全的起步选择。

**3-5个Agent、半结构化任务**：这是编排的黄金区间。Graph State Machine（基于状态图的工作流，如LangGraph）、Fan-out/Fan-in（并行处理后汇总）在这个区间性价比最高。

**5-20个Agent、跨域复杂任务**：必须引入层级隔离。Hierarchical（树状层级）可以把N²冲突拆解为局部冲突，Blackboard（共享知识库）适合多源信息综合的场景。

**20个以上Agent**：你需要认真评估是否真的需要这么多。Swarm（去中心化群集）理论上支持无限Agent，但调试难度是另一个量级。

### 三、选型公式：先算账再动手

在决定"拆不拆"之前，先套这个公式：

**编排价值 = 领域隔离收益 - (Token膨胀 + 延迟累积 + N²冲突成本)**

计算结果为正，多Agent值得做；为负，单Agent + 更多工具就是最优解。

举个实际例子：一个5Agent的报告生成任务，每个Agent处理一个文档子集再汇总。看起来很合理，但算一笔账——5倍的Token、2.5秒的额外延迟、10个需要管理的冲突对——如果这5个文档子集之间没有强依赖，一个Agent分5次处理反而更快更便宜。

## 实际应用

腾讯云2026年8月的工程实践文章中提到了一个企业级案例：某公司用状态机管理多Agent协作流程，把原来需要跨5个系统手动协调的合规审查，拆成了"文档解析Agent → 规则匹配Agent → 风险评估Agent → 报告生成Agent"四步Pipeline。

关键设计决策是：他们没有做成并行的Fan-out/Fan-in，而是选择了串行的Pipeline。原因是合规审查有严格的依赖链——风险评估必须等规则匹配完成，规则匹配必须等文档解析完成。这种确定性强、步骤固定的场景，Pipeline的简单性就是最大优势。

另一篇文章提到，Microsoft在2026年2月发布的Azure Architecture Center指南中，正式把Agent编排归纳为6种设计模式：Sequential、Concurrent、Group Chat、Handoff、Magentic和Hierarchical。值得注意的是，Group Chat模式建议Agent数量不超过3个，否则冲突管理的成本会吞噬协作收益。

## 总结

多Agent系统不是银弹。在你准备拆分Agent之前，先问自己三个问题：

1. **我的单Agent真的到极限了吗？** Google的数据说64%的场景下它还没有。
2. **拆分后的Token成本、延迟、冲突，我算过账吗？** 编排价值公式是你的第一道防线。
3. **我选的编排模式，匹配我的Agent数量和任务结构吗？** 四个甜点区已经帮你分好了。

别为了"看起来先进"而拆分Agent。真正的工程智慧，是在该用单Agent时克制，在该用多Agent时精准。
